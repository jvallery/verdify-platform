# Control model, cross-layer contracts and focused commands

Reference detail for working in this repository. [AGENTS.md](../../AGENTS.md) has the delivery paths and the hazards; this file has the rules that keep firmware, host and database in step.

## Control model

- The controller decides climate alone, every second, with the band-edge law (`firmware/lib/climate_law.h`) and its compiled constants. It reads the house band (the edge anchors the host pushes from `crop_band_anchors`, the one live band store) and the drying cost limit. With no host, no clock or no sensors it keeps running on the rules of section 4.9 of `docs/design/climate-refactor-plan-2026-11-15.md`. Irrigation and lighting keep their own engines in the same loop.
- The host pushes the band, the drying cost limit, the operator switches, the lighting values and the irrigation programs, and confirms each value by its readback. The band and the drying cost limit are the owner's values: they are written only from the dashboard band editor under his sign-in. The remaining settings are the operator's.
- Iris (the Hermes agent `verdify-hermes-iris`) is a once-a-day reviewer. The ingestor wakes it after 07:00 local time, and an admin MCP request (`review_run`) wakes it on demand. It reads the daily record and writes one row to `planner_review`. It writes no climate value: MCP has no plan or tunable write tool, an agent's `set_setting` reaches only the operator switches, and it keeps its irrigation tools.
- The host records the law's state (`system_state` entities `climate_law_state`, `climate_drying_meter` and `climate_law_constants`), the daily record (`daily_record`, `daily_relay_record`: cycles, run time, utilities, drying, compliance), the relay counters (`system_state` entity `relay_counters`, checked against the stored relay events by `v_relay_counter_reconciliation_daily`), the gap log the controller replays after a disconnect (`gap_replay_quarters`) and the controller's health columns on `diagnostics`.
- Alert rules live in jvallery/monitoring-stack. The product metrics are exposed at one point, the operator API's `/metrics` (`api/product_metrics.py`, refreshed on a timer, scraped by the monitoring-stack job `verdify-operator-api`). The ingestor keeps its `alert_log` monitor, which feeds the dashboard's alerts. A `PrometheusRule` under `deploy/k8s/**` is never loaded, and `scripts/check-prometheus-rule-source.py` rejects one.

## Generated files

Edit the source, then regenerate.

- The dashboard ConfigMaps in `deploy/k8s/components/grafana/generated/` come from `grafana/dashboards/`: `python scripts/gen-grafana-dashboard-cms.py`, checked by `make grafana-cm-check`.
- The law's constants come from `verdify_schemas/climate_law.yaml`: `python3 scripts/gen-climate-law-constants.py` generates the firmware header, the Python module and `docs/climate-law-constants.md`, and `make ci` runs it with `--check`. The same check fails when a law source file holds a numeric literal other than 0, 1 or 2. Changing a constant is a firmware release: the controller reports the hash of its compiled constants and the host alerts when it differs from the released file.

## Cross-layer contracts

- **Schemas first.** Land a `verdify_schemas` model and its migration before or with their consumers; `verdify_schemas/tests/test_drift_guards.py` guards the layer boundaries. Every ingestor database write validates through a `verdify_schemas` model, and a new external API input gets a boundary schema in `verdify_schemas/external.py`. Before tightening a write model, check live data for rows that would now fail, because the single ingestor logs and drops any row that fails validation.
- **Migrations.** One numbered file per change, applied in order. Never edit an applied migration: the ledger runner fails closed on a changed hash. Never wrap a self-committing migration (a top-level `COMMIT`, or `CONCURRENTLY`, `VACUUM`, `ALTER SYSTEM` and similar) in an outer `BEGIN … ROLLBACK`: the inner commit lands on the live database. `make migration-rollback-safety` classifies each file. Migrations run forward only; a dropped table comes back only from its archive.
- **Settings.** `verdify_schemas/tunable_registry.py` (with `ALL_TUNABLES` in `verdify_schemas/tunables.py`) is the host and firmware settings contract, and no row is writable by the reviewer. The host side of a firmware output ships and syncs before the flash that publishes it, and the host skips a setting the connected controller does not list. A firmware change that deletes a setting deletes its `ingestor/entity_map.py` rows and turns its registry row off in the same commit, because the drift guards compare both in one tree.
- **Policy wire layout.** The 48-slot layout in `verdify_schemas/policy_vector.py` is frozen to match the firmware's generated headers: five slots are live settings and 43 are reserved (`RESERVED_WIRE_SLOTS`), never written or read. Shrinking it is part of the next firmware change.
- **Readback for every setting** ("rule 6" in code comments). Each new `num_*` or `sw_*` setting in `firmware/greenhouse/tunables.yaml` needs a `cfg_*` readback in `firmware/greenhouse/sensors.yaml`, because a setting pushed without a readback can be corrupted silently.
- **Name the restart** ("rule 7", `scripts/check-service-restart-drift.sh`). A change to `verdify_schemas/**`, `ingestor/entity_map.py` or `mcp/server.py` names its restart in the commit message or pull request body, as `Post-merge restart: verdify-mcp, verdify-ingestor` or `Restart: none — <reason>`, because MCP once served a stale schema for more than 40 hours.
- **Flags and entities.** New override flags go in `firmware/lib/greenhouse_types.h` and every consumer. Renaming or removing an entity in `firmware/greenhouse/controls.yaml` updates `ingestor/entity_map.py`.

## Database objects being retired

Database objects of the retired experiment platform, digital twin and plan cycle are dropped one migration per release, each after an archive is written to the NAS dump volume (PVC `verdify-db-dumps`, subdirectory `archive/`) and checked. Everything the public site reads stays until the site is rebuilt: the plan and forecast tables, their views and functions, and the experiment objects behind its embedded panels.

## Focused commands

- Setup and gates: `make setup` creates the repository `.venv`. `make ci` (`scripts/ci-local.sh`) is the full offline gate, and `CI_BASE_REF=origin/main make ci` adds the diff gates (rules 6 and 7, and the firmware replay diff at `THRESHOLD_PCT=0`). `make lint` and `make format`. `kustomize build deploy/k8s/overlays/prod` renders production.
- Firmware logic (`firmware/lib/**`, `firmware/greenhouse/**`): `make test-firmware` (includes `make test-climate-law`, the law against the reference implementation's vectors), `make climate-law-replay` (the law over the recorded corpus), the closed-loop `make climate-law-sim` (CI only), `make firmware-invariants`, the replay diff (`make firmware-replay-worktree OLD=<ref>` before committing, `make firmware-replay OLD=<base> NEW=HEAD` after), plus `make firmware-replay-band OLD=<base>` for band-curve changes, which the corpus-fed replay reports as zero divergence; then `make firmware-check`.
- Reviewer prompt or model: `make planner-dry` renders the daily review's prompt from a fixture, with no database and no API call, and checks its invariants. After shipping, compare the token use recorded in `planner_review` and investigate a rise above 20%.
- Lab and site: `make site-doctor` plus the checks in [web.md](web.md).

## Firmware delivery detail

- Firmware reaches the controller through the signed path in `docs/runbooks/firmware-signed-artifacts.md` (build, verify and flash Jobs from `scripts/firmware-release-job.py`, then its `pin` step, which needs no host toolchain), or through `make firmware-deploy` or its manual equivalent in `docs/runbooks/k3s-operations.md` section 4. All of them run behind `scripts/firmware-deploy-preflight.sh`.
- `make firmware-deploy` runs the preflight, refuses a dirty tree, compiles, flashes over OTA, runs a sensor-health sweep and defaults to `last-good` for automatic rollback. It passes `FIRMWARE_DB_BACKEND` (default `kube`) through preflight and post-flash verification.
- The preflight blocks on an unresolved critical alert, stale telemetry, or a missing last-good artifact. Its override variables require a written reason. When the accepted last-good artifact is missing, a verified, separately labelled recovery candidate can be supplied as an explicit rollback binary with its SHA-256 and a reason; never relabel that candidate as last-good.
- Every flash reads and logs memory: the heap low-water mark and the largest free block after the flash and after each host reconnect, and any restart after the OTA restart. Thresholds are in the Rollback table of `docs/runbooks/firmware-signed-artifacts.md`.
- There is no bake time, minimum artifact age or release limit for firmware; ship a new build as often as needed.
- Verify with the `diagnostics.firmware_version` query in `docs/runbooks/laptop-operator.md` section 3, not `firmware/artifacts/last-good.version`, which is the rollback floor and lags until a release is promoted.
- To roll back, submit the flasher Job for the rollback release's exact revision and manifest (`python3 scripts/firmware-release-job.py flash --revision ROLLBACK_SHA --expected ROLLBACK_MANIFEST --name NEW_JOB_NAME --submit`, then its `pin`). `make firmware-rollback` needs a host with `firmware/artifacts`, esphome and the OTA secret, and flashes `last-good`. The rollback target is the previous build of the band-edge law. Firmware from before the law is not a rollback target: the host no longer pushes the retired climate settings, so that firmware would run on its boot values. After a rollback to an earlier law build, check the owner-held values by hand, because the host neither pushes nor reads back a retired setting.
